The Harness Hypothesis, Tested

Flagship paper experiment spec - first draft

Status: first draft, open for revision · Track: flagship (sibling to paper-planning/bob-for-hpc/) · Branch: claude/enhance-bob-ai-joR12

This document is the experiment-design spec for the flagship paper claim: holding the model fixed, an orchestration harness that tracks its own confidence calibration, accumulates a versioned findings registry with RecurringPattern promotion, and routes recovery actions through a cost-aware policy strictly dominates undifferentiated retry budgets on completion rate, $ / feature, and reward-hacking incidence.

Five open decisions are flagged at the bottom. Everything else is concrete enough that the engineering items map directly to issues.

1. The falsifiable claims

Six tightly scoped hypotheses. Each is operationalised as a metric difference with a sign.

IDClaimFalsifies if
H1 Holding the model fixed, completion-rate-per-dollar increases monotonically V0 → V1 → V2 → V3. Any adjacent pair shows Vi+1 ≤ Vi with overlapping 95% bootstrap CIs.
H2 bob3's predicted task-class confidence has ECE ≤ 0.10 in V3; V0's elicited confidence has ECE ≥ 0.20. V3's ECE ≥ V0's, or both are ≥ 0.25 (the system is uniformly miscalibrated).
H3 Reward-hacking incidence (Jain rubric - LRU injection, site-customize.py hijack, try/except: pass swallow, test-impl coupling, hardcoded I/O) drops V0 → V3 by ≥ 2×. V3 incidence ≥ V0 / 1.5.
H4 A findings registry trained on specs {S1..S4} reduces refinement attempts on held-out S5 by ≥ 25% vs an empty-registry V3. Reduction < 10% or the CI crosses zero.
H5 RecurringPattern promotion (vs accumulation alone) accounts for ≥ 30% of the V2 → V3 gap. Disabling promotion changes the gap by < 10%.
H6 Semantic-preserving spec perturbations (rename / reorder / red-herring) do not erase the V3 advantage. Perturbed-spec gap < 50% of original-spec gap.

H1 and H3 are the headline results. H2 is the most novel measurement. H4 is the transfer claim. H5 is the mechanism test. H6 is the bench-leakage defence.

Perturbations

For each seed spec, generate 3 semantically equivalent variants via a deterministic perturbation script:

  • P_rename - rename feature ids and criteria identifiers.
  • P_reorder - shuffle criteria order within each feature.
  • P_redherring - insert 1-2 acceptance criteria that are trivially true but plausible-sounding (tests whether the harness is sensitive to noise).

Total: 8 seeds × (1 original + 3 perturbations) = 32 spec instances.

4. The experiments

E1 - Main ablation grid (the headline)

TestsH1, H3, H6
Cells5 variants × 32 spec instances × 3 seeds = 480 runs
Primary metricscompletion rate, $/successful-feature, turns/successful-feature
Secondaryrefinement attempts, wall-clock, regression flips
AnalysisBootstrap 95% CIs on per-spec means; paired comparison across the V0→V1→V2→V3 chain; Holm-Bonferroni across 4 primary metrics

E2 - Calibration measurement

TestsH2
SourceReuse all 480 runs from E1 - every variant emits a uniform predicted_confidence ∈ [0, 1] via the same elicitor (see §5, item 2)
OutputsReliability diagram (10 bins) per variant; ECE; Brier score; per-task_class breakdown

E3 - Reward-hacking incidence

TestsH3 quantitative tail (H3 incidence-vs-completion in E1 only gives binary completion view)
MethodPost-hoc LLM-judge with a 5-attack rubric (Jain-derived) runs on every completed feature's final source diff
ValidationHand-label 100 features (50 clean + 50 with deliberately injected attacks) to measure detector precision / recall before deployment at scale

E4 - Cross-project transfer

TestsH4
DesignTrain V3 on {S1, S2, S3, S4} accumulating the registry. Freeze. Then run V3 on S5 with frozen registry and V3 on S5 with empty registry. 5 seeds per cell = 10 runs
MetricRefinement attempts to completion; reward-hacking incidence

E5 - Pattern-promotion ablation

TestsH5
DesignV3 with RecurringPattern promotion disabled (reviews.py's promote_on_n set to ∞) vs full V3. Run on S1-S8 × 3 seeds = 48 runs
MetricHack incidence, refinement attempts

E6 - Decision-policy gate ablation

TestsWhich gate in docs/failure_handling.md is load-bearing
DesignV3 minus each gate in turn: -RCA, -confidence-decay, -decomposition, -regression-cascade. 4 sub-variants × 8 seeds × 3 seeds = 96 runs
MetricSame as E1

E7 - External baseline comparison

TestsH1 against external systems
DesignVaider and Vcc on all 8 seed specs × 3 seeds = 48 runs
CaveatAider / Cursor have different cost models - report cost on turns and $ both ways

Total runs across all experiments: ~700. At median ~$5/run that is roughly $3.5k, padded to $5k for retries and dev. Open decision - see §9.

5. What bob3 needs to do - engineering work, ordered by dependency

These are the deltas from current main. None require model changes; all are harness-side.

  1. BOB3_ABLATION_MODE config enum - env var plus CLI flag that flips the variant. Each variant maps to a frozen config struct describing: which skills install (skills_installer.py); which MCP plugins enable (mcp_config.py); whether superpowers.run_checks() runs; whether reviews.Registry writes; whether _increment_refinement_attempts decays confidence; whether spawn_rca_agent ever fires; whether the regression cascade triggers. Single switch, no scattered ifs.
  2. Uniform predicted_confidence elicitor - a post-spawn lightweight LLM call, separate from the implementation spawn, that, given the spec plus the produced diff, emits {confidence: float, task_class: str}. Runs identically in every variant. This is the only way H2 is a fair comparison. ~200 LOC; new file src/bob3/calibration_probe.py.
  3. Spec perturbation generator - deterministic, seedable. Reads a YAML spec, applies {rename, reorder, redherring} for a given seed, writes to disk. ~300 LOC; tools/perturb_spec.py. Validated with a round-trip identity test under seed=0.
  4. Reward-hacking detector - post-hoc LLM-judge with the 5-attack rubric. Runs against the final commit's diff. Returns {attack_type: bool} per attack. ~400 LOC plus a 100-feature hand-labeled validation set in paper-planning/harness-hypothesis/labels/.
  5. Telemetry exporter - every run emits a single run.jsonl line with a fixed schema: 
    {variant, spec_id, seed, completion_bool, cost_usd, num_turns,
 refinement_attempts, wall_clock_s, predicted_confidence,
 task_class, hack_detections, registry_hits, regression_flips, ...}
    New module src/bob3/telemetry.py; called from OrchestrationLoop's finally-block.
  6. External baseline runners - tools/run_aider.py and tools/run_claude_code.py. Same spec format in; same telemetry schema out. Sandbox is identical (same container). ~300 LOC each.
  7. Sweep orchestrator - tools/sweep.py consumes a YAML run-plan (variant × spec × seed grid) and dispatches runs in parallel with a cost-budget guard rail (aborts the sweep if total $ exceeds ceiling). Resumable via the existing resource_checkpoints table. ~400 LOC.
  8. Analysis pipeline - an analysis/ directory with notebooks for reliability diagrams, the ablation table, bootstrap CIs, transfer plots, hack-incidence bars. Pure post-hoc on the jsonl artifacts.
  9. Three new spec files - examples/SXX_*.yaml placeholders. Each authored with a hand-written reference implementation stored under paper-planning/harness-hypothesis/references/ so the held-out evaluation has ground truth. Final choice of demos open.
  10. Model and SDK version pin - hard-pin claude-code-sdk and the model id in the variant config; record both in every telemetry line. Defends against drift mid-experiment.

Items 1-5 are blocking. 6-10 can land in parallel.

6. Statistical methodology

  • Binary outcomes (completion rate, hack incidence): Wilson 95% CI; bootstrap on the per-spec mean for pairwise comparison.
  • Continuous outcomes ($/feature, turns): paired bootstrap on the per-spec mean, 1000 resamples, BCa.
  • Calibration: ECE with 10 equal-width bins; Brier score as a secondary scalar.
  • Multiple comparisons: Holm-Bonferroni across the 4 primary metrics in E1, separately within each experiment.
  • Reporting: every figure must be reproducible from the released jsonl plus the analysis scripts. Negative results published alongside.

7. Threats to validity (and mitigations)

ThreatMitigation
Bench leakage - V3 was trained on these specs Perturbations P_* plus 3 new held-out specs (S6-S8)
Hack-detector unreliable - the measurement instrument is itself an LLM Hand-label 100; require precision ≥ 0.85 and recall ≥ 0.80 before deployment
Model drift mid-experiment Pin SDK + model version; complete each experiment within a single 4-week window
Calibration elicitor confound - V0 has no internal confidence Uniform post-spawn elicitor across all variants - this is item 2 above
Stochasticity at N=3 seeds Bootstrap CIs reported on every cell; flag any result whose CI crosses the comparison threshold
Cost-normalisation noise (Max Pro vs API) Report turns as primary, $ as secondary; pin to a single API key type for the headline run
Sandbox escape or interference between runs Each run in a fresh container, fresh workspace, no shared state outside the explicit registry / checkpoint files

9. Open decisions I need before committing the full plan

  1. Budget ceiling. Working assumption is ~$5k for compute across all experiments. Raise or lower?
  2. Model pin. Default: the current pinned Claude model. Or do we want to also run V3 on a smaller model (e.g. Haiku) to show the harness gain scales - at additional cost?
  3. External baselines. Include Aider plus Claude Code (E7), or cut to save scope?
  4. Held-out specs. Final choice for S6, S7, S8 - see the flagship-demos ideation thread. The existing PyQt-based Swedish-circle build is not impressive enough to anchor a flagship paper; what replaces it as the visible showcase is open.
  5. Venue target informs the power calculation. NeurIPS / ICLR (rigorous CIs, possibly N=5 seeds) or workshop first (N=3 fine)?
